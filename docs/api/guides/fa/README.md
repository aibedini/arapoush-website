# راهنمای API برای تیم آراپوش

این راهنما خلاصهٔ فارسی مستندات API است. مرجع کامل و دقیق هر مسیر را در سه جا می‌بینید:

- **مرجع داخلی تعاملی:** داخل کنسول OPEX از منوی «مستندات API» (نشانی `/v1/manage/docs`). همهٔ مسیرهای OPEX، مسیرهای سایت و API شرکا را دارد و می‌شود همان‌جا درخواست امتحان کرد.
- **مرجع عمومی شرکا:** `https://opex.arapoush.com/docs/partner`. فقط API آراسی‌ام‌اس را نشان می‌دهد و هیچ مسیر داخلی در آن نیست.
- **فایل‌ها:** `docs/api/*.openapi.json` (OpenAPI 3.1)، فهرست کدهای خطا `docs/api/errors.md` و مجموعهٔ Postman در `docs/api/postman/`.

## مستندات از کجا می‌آید

مستندات دستی نوشته نمی‌شود. کنار هر ماژول API یک فایل `contract.ts` هست، مثلاً `apps/opex-api/src/tickets/contract.ts`. این فایل برای هر مسیر مشخص می‌کند:

- چه چیزی می‌گیرد: پارامترها، query، بدنه و هدرها، با محدودیت‌هایشان
- چه کسی اجازه دارد: نوع ورود، کمترین نقش و نیاز به تأیید دوباره
- برای هر وضعیت پاسخ چه برمی‌گرداند، با ساختار و نمونه
- چه خطاهایی می‌دهد و هر کدام کِی رخ می‌دهد
- محدودیت تعداد درخواست و رویدادهایی که در گزارش رویدادها ثبت می‌شود

کد هر مسیر ورودی را با همان schemaی قراردادش بررسی می‌کند، پس مستند و کد نمی‌توانند با هم فرق داشته باشند. دستور `pnpm docs:api` همهٔ فایل‌های مستندات را از روی همین قراردادها می‌سازد.

## چه چیزی جلوی کهنه شدن مستندات را می‌گیرد

| بررسی | کجا | اگر رد شود یعنی |
|---|---|---|
| هر مسیر ثبت‌شده دقیقاً یک قرارداد دارد | تست‌های API | مسیری بی‌قرارداد اضافه یا حذف شده است |
| هر پاسخ واقعی تست‌ها با قرارداد می‌خواند | تست‌های API (همهٔ ۱۲۷ مسیر) | پاسخ، کد وضعیت یا کد خطا با مستند فرق دارد |
| فایل‌های `docs/api` با کد یکی است | تست و `pnpm docs:api:check` | قرارداد عوض شده ولی فایل‌ها دوباره ساخته نشده‌اند |
| Redocly lint | `pnpm docs:lint` | سند OpenAPI ایراد ساختاری دارد |
| تغییر شکننده | `pnpm docs:breaking` | چیزی حذف یا سخت‌گیرانه‌تر شده که کلاینت‌ها را می‌شکند |

## اضافه یا عوض کردن یک مسیر

1. قرارداد را در `contract.ts` همان ماژول بنویسید یا به‌روز کنید، با نمونهٔ درخواست و پاسخ و کدهای خطا.
2. در handler ورودی را با schemaی قرارداد بخوانید، مثلاً `TICKETS.note.body.parse(req.body)`.
3. دستور `pnpm docs:api` را اجرا کنید و فایل‌های ساخته‌شده را همراه کد commit کنید.
4. اگر تغییر شکننده است:
   - `API_VERSION` را در `apps/opex-api/src/openapi/specs.ts` بالا ببرید.
   - در پیام commit بنویسید `API-Break: approved <دلیل>`.
   - اگر API شرکا عوض شده، پیش از انتشار به تیم آراسی‌ام‌اس خبر بدهید.

## قواعد مشترک

- **خطاها:** همه `application/problem+json` هستند با یک `code` ثابت. تصمیم را همیشه بر اساس `code` بگیرید، نه متن `detail`. شمارهٔ درخواست در `instance` و هدر `X-Request-Id` می‌آید.
- **ورود در کنسول:**
  - ورود با کوکی و دو مرحله است: گذرواژه و کد برنامهٔ احراز هویت.
  - هر درخواست نوشتنی هدر `X-CSRF-Token` لازم دارد.
  - کارهای حساس تأیید دوبارهٔ هویت در ۵ دقیقهٔ گذشته را می‌خواهند.
- **نقش‌ها:** بیننده < حسابرس < اپراتور < مدیر ارشد. حسابرس هیچ‌وقت چیزی را تغییر نمی‌دهد.
- **ویرایش همزمان:**
  - برای ذخیرهٔ محتوا باید شمارهٔ نسخه‌ای را که باز کرده‌اید بفرستید.
  - اگر در این فاصله کس دیگری آن را تغییر داده باشد، خطای `CONFLICT_BASE_REVISION` برمی‌گردد.
- **حریم خصوصی:**
  - پاسخ فرم‌ها و پیام تیکت‌ها رمزگذاری‌شده نگه داشته می‌شود.
  - گزارش رویدادها هیچ اطلاعات شخصی ندارد.
  - هر بار دیدن تیکت یا پیوست ثبت می‌شود.

راهنمای انگلیسی همین قواعد در [conventions.md](../conventions.md) است. نحوهٔ ارسال webhook و بررسی امضای آن در [webhooks.md](../webhooks.md) آمده.

## Postman

1. فایل `docs/api/postman/opex.postman_collection.json` و یکی از فایل‌های محیط (`local` یا `staging`) را import کنید.
2. برای مسیرهای کنسول اول «Sign-in and sessions → Step 1» و بعد «Step 2» را بفرستید. توکن CSRF خودکار ذخیره می‌شود.
3. مسیرهای شرکا امضای DPoP و RFC 9421 لازم دارند. برای آن‌ها از کلاینت PHP مرجع استفاده کنید.
4. در فایل‌های محیط هیچ‌وقت رمز یا توکن پروداکشن نگذارید.
