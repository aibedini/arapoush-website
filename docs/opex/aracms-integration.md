# AraCMS ↔ OPEX integration guide

AraCMS (the client's PHP panel) never writes website content directly. It reads what it has been
granted, uploads media and **proposes changes** as change requests (CRs). OPEX decides each CR by
policy (auto-approve, review, or deny), records everything in its tamper-evident audit log, and
publishes to the website.

- API reference (OpenAPI 3.1): `GET {OPEX}/v1/partner/openapi.json`
- Reference PHP client: [`clients/php-reference`](../../clients/php-reference) (PHP 8.3, Guzzle,
  ext-openssl)
- Sandbox: a separate OPEX instance with `TENANT=arapoush-sandbox` and seeded content (§8)

## 1. Onboarding

1. **AraCMS** generates two P-256 key pairs on its server:
   - the **client key**, for token-endpoint authentication and request signing;
   - the **DPoP key**, which binds tokens to the AraCMS server.

   Private keys never leave that server.
   ```php
   file_put_contents('/etc/aracms/opex-client.pem', Es256::generate());
   file_put_contents('/etc/aracms/opex-dpop.pem', Es256::generate());
   echo json_encode($opex->clientPublicJwk());   // send this to the OPEX team
   ```
2. **An OPEX super admin**, in Console → Partners → New partner, enters:
   - the public JWK;
   - the AraCMS server's outbound IPs (CIDR);
   - the exact redirect URI(s), for example `https://cms.example.com/opex/callback`;
   - the scopes;
   - optionally an mTLS certificate fingerprint.

   OPEX returns a `client_id` (`aracms_…`).
3. **The OPEX team** (grants, policies and webhooks are on the management API today; their console screens arrive in P7):
   - creates AraCMS users (Console → Partners → Users), each with a role such as `aracms_editor`;
   - grants that role access to content types, fields and languages (Grants, §5);
   - sets the webhook URL. The webhook secret is shown once.

## 2. Signing in (OAuth 2.1)

```mermaid
sequenceDiagram
  participant U as AraCMS user
  participant A as AraCMS server
  participant O as OPEX
  U->>A: "Connect to OPEX"
  A->>A: code_verifier, state (session)
  A-->>U: 302 /oauth/authorize?…&code_challenge=S256(verifier)
  U->>O: password + authenticator code (TOTP; first time: set up)
  O-->>U: 303 redirect_uri?code=…&state=…
  U->>A: callback (check state)
  A->>O: POST /oauth/token (code, verifier, client_assertion=private_key_jwt, DPoP proof)
  O-->>A: access_token (DPoP-bound, 5 min), refresh_token (rotating, 8 h)
```

**Token rules:**
- **Access token:** the access token is bound to the DPoP key. Every API call sends
  `Authorization: DPoP <token>` and a fresh `DPoP` proof (`htm`, `htu`, `iat`, `jti`, `ath`).
- **Refresh token:** refresh tokens rotate. Store the newest one. Presenting an old one revokes the
  whole session (theft detection).
- **Machine jobs:** jobs without a user use `client_credentials` and are limited to grants on the
  partner client itself.
- **Network checks:** every request is checked against the client's IP allowlist, and its mTLS
  certificate when one is configured.

The PHP client does all of this:
- `authorizationUrl()`, `exchangeCode()` and `refresh()` handle sign-in;
- `tokens()` and `withTokens()` let AraCMS store tokens per user, encrypted.

## 3. Writing: signatures and idempotency

Every `POST` must carry:

| Header | Meaning |
|---|---|
| `Idempotency-Key` | A UUID. Retrying with the same key and body returns the first answer (`Idempotent-Replayed: true`). The same key with another body returns 409 `IDEMPOTENCY_KEY_REUSED`. |
| `Content-Digest` | `sha-256=:<base64>:` of the exact body bytes (RFC 9530). |
| `X-End-User-IP` | The AraCMS user's IP. It is recorded in the audit log next to the AraCMS server's IP. |
| `Signature-Input` / `Signature` | An RFC 9421 signature with the client key. |

**Signature requirements:**
- `alg="ecdsa-p256-sha256"` and `keyid` = your JWK `kid`.
- The signature covers `"@method" "@path" "idempotency-key"`, plus `"content-digest"` when there is a
  body, plus `"x-end-user-ip"` when sent.
- `created` must be within ±60 s, and `nonce` (16+ characters) is used once.

`RequestSigner::sign()` builds the signature. `tests/vectors.json` is generated by the OPEX server
code, and both test suites check it, so the PHP and Node sides cannot drift apart.

## 4. Reading and proposing

```php
$draft = $opex->content('page.printing');          // only granted fields and languages
$cr = $opex->proposeChange('Flexo summary update', [
    ['entry' => 'page.printing', 'base_revision_id' => $draft['base_revision_id'],
     'path' => '/tech/items[id=flexo]/summary', 'locale' => 'fa', 'value' => '…'],
    ['entry' => 'page.printing', 'base_revision_id' => $draft['base_revision_id'],
     'path' => '/images/tubeGold', 'value' => ['asset' => $upload['asset'], 'alt' => ['fa' => '…']]],
], note: 'Per sales team', endUserIp: $_SERVER['REMOTE_ADDR']);
// → ['id' => 'cr_…', 'state' => 'pending_review' | 'approved' | 'published' | 'rejected', 'decision' => [...]]
```

**Paths:**
- A path addresses a field: `/a/b`, a list item by key `[id=flexo]`, or by index `[0]`.
- Localized text changes one language per item (`locale`).
- `op: insert` appends an item to the list at `path` and needs the `entry.create` grant.
- `op: remove` deletes the item at `path` and needs the `entry.delete` grant.

**Media:**
- Upload with `uploadMedia($bytes, 'name.jpg')`. The body is the raw file, signed like any write.
- Images are re-encoded to WebP and stripped of metadata. SVG and PDF files with scripts are
  rejected.
- Use the returned `asset` id in image values.

`GET /v1/partner/schema` lists the types and fields you may read (`schema`) and propose
(`proposable`), with labels and limits, so AraCMS forms can be generated from it.

## 5. Grants

Operators grant access to a role, a single user or the whole client:

```json
{ "subject_kind": "partner_role", "subject_id": "aracms_editor",
  "scope": { "types": ["page.printing", "page.home.*"], "fields": ["/hero/**", "/tech/**"],
             "exclude": ["/hero/features/**"], "locales": ["fa", "en"] },
  "actions": ["read", "propose", "media.upload", "cr.withdraw"] }
```

**Rules:**
- Access is denied by default, and `exclude` wins over `fields`.
- Locked fields (3D geometry, sizes, ids, renders) and operator-only fields (guide scoring, contact
  details, layout) are never granted.
- Fields you may not read are **omitted** from responses, not nulled.
- Every refusal is logged as `authz.denied`.

## 6. Change request lifecycle

```
submitted ─► pending_review ─► approved ─► published
    │              │  └► rejected      ▲
    │              └► needs_rebase ─ resubmit ┘ (back through policies)
    └► withdrawn / expired (30 days idle)
```

**Policy decision on submit:**
- Policies may auto-approve, and optionally auto-publish, small edits. For example: edit ratio
  ≤ 20 %, no links, office hours in Tehran, at most N per hour.
- Some rules always require review:
  - more than 50 items;
  - link changes on site-wide content;
  - media whose scan is still pending.

**Review:**
- Operators may approve some items and reject others, with a reason per item.
- Operators may amend a value before approving. The amended item is marked `by_operator`; your
  original item stays, rejected.
- Some CRs need two operators (four-eyes).

**Conflicts:**
- If someone changes the same field first, the CR moves to `needs_rebase` with
  `conflicts: [{path, expected, current}]`.
- To continue, re-read the content and call `resubmit($id, ['page.printing' => $newBase])`.

**Preview:** `preview($crId, 'fa')` returns a 30-minute link to the website with the CR applied.

## 7. Webhooks

OPEX POSTs these events to the webhook URL:
- `cr.state_changed`, with data `{cr, state, conflicts?}`;
- `content.published`.

Each request is signed `OPEX-Signature: t=…, v1=hex(HMAC-SHA256(secret, t + "." + body))`.

```php
$event = Webhook::verify($secret, $_SERVER['HTTP_OPEX_SIGNATURE'] ?? null, file_get_contents('php://input'));
if ($event === null || alreadySeen($event['id'])) { http_response_code(401); exit; }
```

- Reply `2xx` within 10 s.
- Failed deliveries retry with backoff (1 minute to 6 hours, 24 attempts), then become dead letters.
  Dead letters are visible to operators, who can retry them.
- Delivery is at-least-once, so de-duplicate by `id`.

## 8. Errors and sandbox

Errors are RFC 9457 `application/problem+json` with a stable `code`. `OpexException::$problemCode`
carries it.

| Code | Meaning |
|---|---|
| `GRANT_DENIED` | No grant for this type, field, language or action |
| `FIELD_LOCKED` | The field cannot be changed by partners |
| `VALIDATION_FAILED` | `issues[]` with exact paths (bidi controls, URL schemes, lengths…) |
| `PATH_NOT_FOUND` / `BAD_BASE_REVISION` | Wrong path, or a base revision of another entry |
| `IDEMPOTENCY_KEY_REQUIRED` / `IDEMPOTENCY_KEY_REUSED` | See §3 |
| `UNKNOWN_ASSET` | The asset doesn't exist or belongs to someone else |
| `CR_STATE` | The CR is not in a state that allows this |
| `SCOPE_DENIED` / `NETWORK_DENIED` | The token scope, IP or certificate doesn't allow it |
| 401 | Token, DPoP or signature invalid or expired |
| 429 | Rate limited; retry with backoff (same Idempotency-Key) |

**Sandbox:** run OPEX with `TENANT=arapoush-sandbox` and its own database. Content is imported from
the website on first start. Integrate there first; production credentials are issued after a
successful run through §2–§7.
